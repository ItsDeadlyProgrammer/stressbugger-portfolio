# LLM Integration

The LLM does the creative work: it reads the statement and writes programs and explanations. It is treated as an
**untrusted, fallible contributor**. Everything it produces is data that must pass execution checks; nothing it says
is a verdict.

## Layers

```
LlmService ── fills prompts/<id>.md, validates the JSON answer against prompts/schemas/<id>.json,
   │          retries once with the error, backs off on overload, caches in Redis, logs every call
   ▼
LlmClient ─┬─ OllamaLlmClient    (default, local, free, streamed)
           ├─ GeminiLlmClient    (optional, cloud; used by the hosted demo)
           ├─ AnthropicLlmClient (optional, cloud; Spring AI)
           └─ MockLlmClient      (offline demos and end-to-end tests)
```

- The provider is chosen by one setting, `STRESSBUGGER_LLM_PROVIDER`. No other code knows which model is used.
- **`LlmService` is the only gateway.** The pipeline asks for a template id and variables and gets back
  schema-valid JSON, or a clear error.

## Prompt templates

Prompts are versioned Markdown files with a front-matter header (`id`, `version`), a `# System` and a `# User`
section, and `{{placeholders}}`. Each has a matching JSON Schema.

| Template | Produces |
|---|---|
| `constraints` | variables with bounds, brute-force limits, multi-test flag, output comparison rules |
| `format` | a structured model of the input format, used by the shrinker |
| `samples` | sample tests, only kept if they appear verbatim in the statement |
| `validator` | a program that accepts valid inputs and rejects broken ones |
| `generator` | a seeded generator plus a plan of strategies with their arguments |
| `checker` | an output checker for "print any valid answer" problems |
| `brute` | an independent brute force with a given approach and language |
| `property` | property checkers for large inputs where no brute force can run |
| `explain` | root cause with cited lines |
| `fix` | a patched solution and a description |
| `tags` | bug tags such as `overflow`, `off-by-one`, `reset-missing`, `edge-case` |

Template versions are recorded in every session's summary, so results can be traced to the exact prompts that
produced them.

## Reliability

| Problem | Handling |
|---|---|
| Answer is not valid JSON or does not match the schema | retried once with the validation error appended |
| Rate limit or overload | exponential back-off |
| Program does not compile or fails a check | **self-repair:** the error goes back to the LLM, up to 3 attempts per program |
| Program still fails | rejected; the session continues with what it has and confidence is lowered |
| Answer cut off | detected and reported (raise the context or output limit) |
| Model hallucinates a sample | dropped: samples must appear verbatim in the statement |
| Model cites a line that does not exist | the dashboard says whether cited lines exist in your code |

## Caching

Answers are cached in Redis, keyed by a hash of provider, model, template version, variant, attempt and the rendered
prompt. A cached answer is **only a proposal**: every program in it is compiled and qualified again in each session,
so a cache hit never reuses execution evidence.

## Observability

- Every call (and cache hit) is stored in `llm_calls`: template, version, model, input and output tokens, latency,
  cost and success.
- During a call the dashboard receives an `LLM_ACTIVITY` heartbeat every second: elapsed time, tokens written so far
  and the latest text. A stalled call is flagged.
- Time estimates come only from earlier answers to the same template and are labelled as estimates.

## Working with small local models

The default is a free local model (`qwen2.5-coder:7b` on Ollama). Real runs with small models surfaced problems that
the design now handles:

- **Generator plans that ignored their arguments** or used huge sizes in "small" tests. The backend now gives exact
  bounds per strategy, normalises the plan and judges each strategy separately, dropping only the broken ones. On demo
  01 this cut a 19+ minute run to 11.5 minutes.
- **Answers constrained to the JSON schema** (Ollama structured output) remove most formatting failures.
- **A weak model can only cause rejected programs, never a wrong verdict**, because verdicts come from execution.

Measured on a CPU-only laptop: demo 07 with `qwen2.5-coder:7b` found the `SOLUTION_BUG`, explained it and verified the
fix in 414 s. With Gemini on the hosted demo, the three recorded sessions took between 3 and 7 minutes.

## Security boundary

- The LLM only fills JSON documents validated against schemas.
- No tool use, no shell, no file path or command is ever taken from an answer; program ids are generated by the
  backend.
- The backend alone decides what is compiled, with which limits, and what is run.
