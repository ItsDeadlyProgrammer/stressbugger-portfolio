# Sandbox & Security

StressBugger runs code it did not write: your solution, every program the LLM writes and every fix it proposes.
**All of it is treated as hostile.** LLM answers are untrusted data, never instructions.

## Threat model

| Asset | Threat | Defence |
|---|---|---|
| The host | sandbox escape, resource exhaustion | hardened container per session, limits, no network |
| The evidence | a program overwrites the oracle or the recorded output | a separate user for untrusted programs, cleanup after every run |
| Other sessions | interference | one container per session, removed afterwards |
| The machine's CPU | strangers running code on a public server | access token, queue limit, CORS allow-list |
| Secrets | leaking keys or passwords | kept in `.env` only; never in Git, images, the frontend, logs or `/api/health` |

## The sandbox container (Docker mode)

Each session gets one long-lived container, started with:

| Flag | Effect |
|---|---|
| `--network none` | no network at all |
| `--read-only` + size-limited tmpfs | read-only system; scratch space is bounded and disappears afterwards |
| `--memory 1g --memory-swap 1g` | memory cap |
| `--cpus 2` | CPU cap |
| `--pids-limit 256` | stops fork bombs |
| `--cap-drop ALL` (+ `SETUID`, `SETGID`, `KILL`) | almost no privileges |
| `--security-opt no-new-privileges` | setuid binaries cannot gain privileges |
| `--init`, `--ulimit core=0` | zombie reaping, no core dumps |

These are safety boundaries, not quotas: raise them on a bigger machine, never remove them.

## A separate user for untrusted programs

A subtle threat in a stress tester is **evidence tampering**: a malicious or buggy program could overwrite the brute
force so that it "agrees", or edit the recorded outputs.

- The harness compiles programs into a folder only it can write.
- Every untrusted program runs as **uid 10002** with no capabilities, in the only writable folder.
- After every run, the harness kills all of that user's processes and deletes its files.

So a program cannot overwrite another program, touch the harness or the recorded outputs, or leave anything behind for
the next run.

## Per-run limits

| Limit | How |
|---|---|
| wall-clock time | timeout per run, process group killed |
| CPU time | `RLIMIT_CPU` |
| memory | `RLIMIT_AS`; Java uses `-Xmx` instead |
| output | 16 MiB cap, then the program is stopped |
| environment | clean: no backend variables reach a program |

## Attack tests

`sandbox/test/run_harness_test.py` attacks the sandbox on every CI run:

- memory hogs and endless output,
- infinite loops and a fork bomb,
- a detached daemon that tries to outlive its run,
- writes to other programs' files and to `/etc`,
- network access.

## The Docker socket

The backend starts sandbox containers through the host's Docker engine, so the backend container mounts
`/var/run/docker.sock`. That gives the **backend** (trusted code) control of Docker; untrusted programs never see the
socket. For stronger isolation, a runtime such as gVisor (`runsc`) can be set as Docker's default runtime.

## Process mode (hosts without Docker)

Free hosting platforms such as Render do not offer Docker inside a service. For the public demo, the harness runs as a
child process in a private temporary directory, with an empty environment and the same per-run limits, but without a
container: no network isolation, no process limit, and the same user as the backend.

What still protects the deployment:

- **Secrets stay out of reach:** the entry point hands them to the backend in a private file that is deleted as soon as
  the backend starts listening, and removes them from the backend's environment.
- **Local services are locked:** Redis listens on 127.0.0.1 only, with a random password.
- **The platform's own container** limits what a program can reach.

Process mode is meant for a public demo on a disposable host. Docker mode is used everywhere else.

## The LLM never controls execution

- The LLM only fills JSON documents validated against schemas.
- The backend alone decides what is compiled, with which limits, and what is run.
- No tool use, no shell, no path or command taken from an answer; program ids are generated by the backend.
- LLM-written programs must compile, pass the samples and agree with others before they are trusted.

## Network exposure

- **Local:** every published port is bound to `127.0.0.1`; Ollama is not published at all.
- **Server:** only Caddy listens (80/443) with automatic HTTPS. The production overlay refuses to start without an
  access token and a database password.
- **Access token:** protects every endpoint except `GET /api/health`, compared in constant time. The SSE stream accepts
  it as a query parameter because browsers cannot send headers to `EventSource`.
- **CORS:** off unless an allowed origin is configured.
- **Abuse limits:** bounded running and waiting sessions (then HTTP 429); request bodies are size-limited.
- **No SSRF:** the backend only calls configured URLs and the two Codeforces hosts, with a validated problem id.

## Web application

- **XSS:** React escapes all text; program output is shown as plain text.
- **SQL injection:** only bound parameters.
- **Paths:** no user-supplied file names are ever used.
- **Logs:** statements, code and outputs are not logged.
- **Secrets:** the frontend bundle contains only the API URL; `/api/health` reports statuses and versions, never URLs
  or keys.
